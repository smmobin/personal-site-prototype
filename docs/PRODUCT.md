# سیستم پروداکت منیجمنت

این سند قرارداد دائمی پروژه است. مالک نباید هر نوبت این نکات را تکرار کند. هر چت اول همین فایل را می‌خواند.

## هدف نقش‌ها

دو چت جدا، یک ریپو:

| چت | کار | Git |
| --- | --- | --- |
| Product Manager (پایدار) | محدوده، اسپک، اولویت، پرامپت اجرا، QA | فقط این چت بعد از تست سبز commit و push می‌کند |
| Implementer (یک‌بارمصرف) | پیاده‌سازی همان پرامپت | commit/push ممنوع |

## گردش کار

1. مالک در چت PM می‌گوید چه می‌خواهد.
2. PM اسناد را می‌خواند (`README`, `SPEC`, `STRUCTURE`, `PRODUCT`, `TESTING`).
3. اگر درخواست با اسپک تضاد دارد، قبل از پرامپت می‌پرسد.
4. PM یک پرامپت کامل از روی `docs/prompts/IMPLEMENTER.template.md` می‌دهد.
5. مالک آن را در **چت جدید** paste می‌کند و اجرا می‌شود.
6. مالک به PM می‌گوید: «انجام شد».
7. PM `git status` / `git diff` می‌بیند، `npm run verify` را اجرا می‌کند، و در تغییر UI مسیر را در مرورگر هم چک می‌کند.
8. اگر رد شد: باگ‌ها را در پرامپت Implementer بعدی می‌نویسد. push نمی‌کند.
9. اگر قبول شد: `git add` (بدون `.env` و اسرار) → `git commit` → `git push origin` → ریپو، شاخه، hash را گزارش می‌کند.

## قوانین غیرقابل مذاکره

- پاسخ به مالک فارسی و RTL است.
- محتوا ساختگی می‌ماند؛ دادهٔ واقعی مالک وارد سایت نمی‌شود.
- فرم تماس بک‌اند ندارد.
- `index.html` را مستقیم در مرورگر باز نکن؛ فقط `npm run dev`.
- پوشهٔ قدیمی `Mobin` منبع نیست.
- Implementer بدون پرامپت PM شروع به «بهبود کلی» نمی‌کند.
- PM فیچر محصول را خودش پیاده نمی‌کند مگر مالک صریحاً بگوید در همین چت انجام شود.
- تست شکسته = تغییر ناتمام. commit فقط بعد از سبز بودن تست‌های مربوط.

## وقتی PM باید اسناد را به‌روز کند

هر تغییر ماهوی که رفتار، محدوده، استک یا ساختار را عوض کند باید همان نوبت در `SPEC` / `STRUCTURE` / `TESTING` / `README` منعکس شود. اسپک کهنه یعنی بدهی محصول.
